## 已确认的调用链

`home.cpp` 的六个按钮使用 pressed/released：按下调用 `jogGimbal`，松开调用 `stopGimbal`。`GimbalControlClient` 直连 PLC Modbus TCP；与工控机相机 HTTP 服务无关。

| 轴 | 控制寄存器 / 值 | 反馈寄存器 | 当前软限位 |
|---|---|---|---|
| 升降 | 0：1 上升、2 下降 | 101，signed int16 | -1900～6000 |
| 水平 | 2：2 左旋、1 右旋 | 102 | 5～175 |
| 俯仰 | 1：2 上仰、1 下俯 | 103 | 95～265 |

当前仓库与运行目录 `bin/config.json` 的该配置一致。点动用 FC06 单寄存器写，停止用 FC16 将 0..2 清零；状态用 FC03 读取 100..106。旋转轴最大按住时间 1500 ms，升降按住持续，均松手停止。点击不是固定时长自动运行。

客户端连接后仅开展状态/命令处理，没有已定义的舵机初始化、使能或模式切换流程。`commandSucceeded` 只代表收到符合现有解析条件的 Modbus 应答，首页却显示“某动作 成功”；没有基于角度变化确认执行。FC06/FC16 当前也未完整校验回显地址和值/数量。上述是可观察性/协议校验缺口，不能直接认定为本次旋转失效的根因。

原 [首页云台控制开发方案](首页云台控制开发方案.md) 已记载“写入可读回但不动作”与未知底层触发条件，也记录过目标值越限卡住抖动。历史脉冲成功不证明冷启动、复位或闲置后的初始化链完整。旧 `0x2b0` 目标值路线和未知 coil 不作为修复捷径。

## 当前判断与解决路径

优先检查 PLC 侧旋转轴初始化、遥控器与 Modbus 分支的处理差异、使能/模式及目标角状态。遥控器操作后恢复说明状态被改变，和“舵机永久损坏”不吻合；仍不能排除供电、休眠/保护或机械负载等硬件诱因。

现场下一步需要在失效状态下保留原状，并关联同一次按下/松开：

| 证据 | 能区分的问题 | 确认后的修复位置 |
|---|---|---|
| 首页拒绝原因、审计初始角度 | 限位/未获状态/按钮处理 | Tenco 输入或反馈校验；保留机械保护 |
| FC06 原始请求及回显、0..2 的变化 | 未发送、未应答、错误回显、写入被覆盖 | Tenco 通信或 PLC 接口；不能用 UI accepted 代替 |
| PLC 两路来源分支、轴 ready/enable/mode、内部目标角 | 遥控器才初始化、网络分支缺少触发、残留目标或竞争写入 | PLC/驱动程序；在上电/复位时显式安全初始化，两种来源共用执行路径 |
| 控制输出与实际轴动作/角度反馈 | 未产生 PWM/串口控制、输出存在但机构不动、反馈失真 | PLC 输出/反馈或舵机供电/驱动/机械链 |

如果确认网络分支遗漏使能/初始化，应按厂家协议执行“有效角度读取→初始化目标为当前位置→正确模式/使能→ready→点动”，避免上电先运动或跳到旧目标。若为休眠策略，需要厂家确认唤醒方式和状态反馈；不默认用遥控器预转或启动时自动摆动解决。若 PLC 正确输出仍不动作，再检查电压/峰值电流、保护/错误码及负载，不依据软件读数单独判换舵机。

Tenco 后续适合将“命令已应答”“反馈角度变化”“未观察到变化/状态不可信”分开，持久化关联请求/应答/初末角度；反馈变化也不能在缺少独立测量时等同实际机械角。该软件完善尚未实施，不能标成已修复。
