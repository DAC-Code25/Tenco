## 实测结论与证据

HTTP 服务可访问，但相机采集已失败。`GET /camera/status` 两次均返回 HTTP 200，业务状态如下：

```json
{
  "success": false,
  "cameraConnected": false,
  "message": "capture loop error: Communication exception - possible device error/misconfiguration. Original message 'Couldn't read data from stream: 'preview' (X_LINK_ERROR)'",
  "previewWidth": 960,
  "previewHeight": 540,
  "previewFps": 15
}
```

这确定失败点在服务端 DepthAI/OAK `preview` 采集链。X_LINK_ERROR 还不能区分 USB 断连/供电、设备复位、占用、SDK/固件或 pipeline 配置，须结合目标机日志判断。

| curl 默认头 | 200 / multipart/x-mixed-replace | 45841 / 1 | 2.002794 s |
| Tenco 的 User-Agent/Accept/keep-alive 头 | 200 / multipart/x-mixed-replace | 45841 / 1 | 2.002658 s |
| 再次独立请求 | 200 / multipart/x-mixed-replace | 45841 / 1 | 2.002454 s |

三次 curl 均退出码 0，未到 8 秒测试上限；相同响应体 SHA256 为 `125afabc3bfb3e134e3303b9f2209b8d26e05c2c69be2dd19d558c91a147e5ad`。首个 multipart 分块包含一张长度 45766 字节、960×540 的 JPEG。结合状态错误及三次完全相同图片，可确认连接收到的是未更新的缓存帧。服务随后结束响应，具体结束分支/约 2 秒等待常量尚未读取部署源码。响应头 `Connection: close` 本身允许流式 HTTP，不应单独据此认定错误。

## 客户端行为解释

- `VideoClient::start()` 未设置 2000 ms 视频传输超时；`video.reconnectIntervalMs=2000` 控制结束后的等待。`cameraRequestTimeoutMs=5000` 作用于相机控制/状态请求，不是视频流截止时间。
- `handleStreamFinished()` 收到正常 EOF 后清理 reply 并安排重连。curl 独立复现相同 EOF，当前证据不支持把 Qt finished/worker 解码认定为断流源。
- worker 成功解码首张 JPEG 后，`frameReady` 回调把 `m_reconnectAttempt` 重置为 0；连接结束后安排 2000 ms 延迟并增加为 1。每次连接都收到缓存帧，因此一直记录 attempt 1。
- 仓库配置与实际 `bin/config.json` 的视频地址一致；服务实际预览参数为 960×540@15，而客户端配置 1280×720@30 不是设置远端 pipeline 的请求。这一差异不能单独当作 X_LINK_ERROR 原因。
- finished 日志缺少 HTTP/帧数诊断，另状态查询业务失败路径不发出 statusReceived；服务错误可能只在首页首次可见状态变更时显示。这是后续诊断可改进项，不是已证明的断流根因；本任务保持现有产品行为。
