# Tenco 多垄穿梭作业闭环系统开发方案

## 1. 文档目标

本文档重新定义 `Tenco` 在垄间作业场景下的系统架构。

这里要解决的不是“单条直线能不能走”，而是下面这类更真实的作业流程：

- 在一条垄间先往返作业
- 到端点后出垄
- 原地转向 90°
- 短距离转场
- 再转向对准下一条垄
- 在下一条垄间继续往返
- 再回到原来的垄间循环执行

结论先行：

- 这不是蛇形路径
- 这也不应该被做成一条连续的普通导航轨迹
- 正确做法是分层：`通用导航底座 + 作业任务模板 + 本地执行状态机`

本方案要同时满足两类需求：

- 通用场景下仍能使用地图规划与普通导航
- 垄间场景下能稳定执行多垄穿梭、端点掉头、短转场、停靠与恢复

---

## 2. 需求澄清

### 2.1 你当前真实需要的动作

当前场景不是蛇形，而是：

1. 单垄内 A -> B 往返
2. 结束后出垄
3. 原地旋转约 90°
4. 直线短转场
5. 再原地旋转约 90° 对准下一垄
6. 在下一垄内 B -> A 往返
7. 再按相同逻辑回到原来的垄间

### 2.2 为什么不能只用普通路径跟踪

普通路径跟踪适合：

- 任意起终点路径
- 复杂地图
- 不规则运动

但它不擅长：

- 反复执行固定作业模板
- 端点掉头后的重新切线
- 跨垄短转场
- 任务中间的停靠点触发

所以本项目不应该把垄间作业做成“画一条线然后一直追点”。

---

## 3. 总体原则

### 3.1 保留通用能力

普通地图导航必须继续保留，作为：

- 通用兜底能力
- 非垄间场景能力
- 非规则任务能力

### 3.2 垄间作业做成模板

垄间作业应该做成任务模板，而不是写死在普通导航里。

### 3.3 控制闭环下沉到工控机

高频控制必须在工控机本地完成，不放在上位机远程闭环里。

### 3.4 任务层与控制层分离

- 上位机负责任务编辑、显示、下发、监控
- 工控机负责任务执行、控制仲裁、状态机、保护
- 底盘控制器负责最终速度执行

---

## 4. 推荐系统架构

```text
上位机 Qt 项目
  ├─ 地图编辑
  ├─ 普通导航任务
  ├─ 垄间作业任务模板
  ├─ 任务配置与状态显示
  └─ 人工接管入口

无线网络
  └─ 只传任务、状态、日志、低频控制命令

工控机
  ├─ 融合位姿输出
  ├─ 垄间作业执行器
  ├─ 任务状态机
  ├─ 运动仲裁
  ├─ 底盘桥接
  └─ HTTP/ROS 网关

底盘控制器
  └─ 接收最终速度命令并执行
```

## 5. 任务模型

### 5.1 底层原语

底层只保留三类原语：

- `RowLeg`
  - 一条垄内的直线作业段
- `TransferSegment`
  - 两条垄之间的短转场段
- `TurnAction`
  - 原地转向动作

### 5.2 任务模板

在原语之上组装任务模板：

- `SingleRowLoop`
  - 单垄往返
- `MultiRowShuttle`
  - 多垄穿梭
- `CustomMission`
  - 自定义顺序任务

### 5.3 推荐数据结构

建议把任务拆成：

- `MissionPlan`
  - 总任务
- `MissionRowLeg`
  - 某一条垄的往返段
- `MissionTransfer`
  - 垄间转场段
- `MissionCheckpoint`
  - 段内中间点

### 5.4 关键原则

- 中间点是“事件点”，不是再去追一个二维点
- 每条垄仍然保留 A/B 端点示教
- 多垄任务由若干条垄段和转场段拼接而成
- 通用导航仍然存在，但不替代作业模板

## 6. 上位机侧方案

### 6.1 上位机职责

上位机负责：

- 地图编辑与任务编排
- 垄间任务模板选择
- A/B 端点示教
- 中间点配置
- 任务启动/暂停/恢复/停止
- 状态展示与日志展示

### 6.2 上位机当前基础

当前分支已经具备的基础是：

- 地图模块
- 路径规划与显示
- `rowWork` 计划持久化
- `RowWorkClient` 通信骨架
- 右侧任务页签
- `rowMission` 多垄任务数据模型
- 右侧多垄任务编辑器（单垄原语 + 任务编排）

这意味着当前代码已经适合作为“任务编辑层”的起点。

### 6.3 UI 设计建议

地图页建议分成三层：

- 左侧：地图编辑工具，保持滚动式布局
- 中间：地图画布
- 右侧：任务页签

右侧任务页建议分成：

- `常规任务`
- `垄间作业`

其中 `垄间作业` 再分：

- `单垄模板`
- `多垄模板`
- `自定义序列`

### 6.4 多垄作业 UI 逻辑

建议交互顺序如下：

1. 选择任务模板
2. 示教第一条垄的 A/B 点
3. 添加该垄的中间点
4. 添加转场段
5. 示教下一条垄
6. 继续累积任务步骤
7. 统一下发到工控机

### 6.5 上位机接口建议

建议继续保留类似以下接口抽象：

- `GET /row-work/status`
- `GET /row-work/plan`
- `POST /row-work/plan`
- `POST /row-work/capture-pose`
- `POST /row-work/start`
- `POST /row-work/pause`
- `POST /row-work/resume`
- `POST /row-work/stop`

如果后续扩展到多垄任务，建议新增：

- `GET /row-mission/status`
- `GET /row-mission/plan`
- `POST /row-mission/plan`
- `POST /row-mission/start`
- `POST /row-mission/pause`
- `POST /row-mission/resume`
- `POST /row-mission/stop`

### 6.6 当前项目中建议新增的逻辑边界

当前 `RowWorkPlan` 适合作为“单条垄作业原语”。

下一步不建议直接把它改成一个混杂所有逻辑的大对象，而应该新增上层任务对象，把：

- 垄内控制
- 垄间转场
- 任务循环

分开描述。

## 7. 工控机侧方案

### 7.1 工控机职责

工控机负责：

- 继续输出融合位姿
- 执行任务状态机
- 执行直线保持控制
- 执行端点掉头
- 执行垄间转场
- 做控制权仲裁
- 对外提供网关接口

### 7.2 推荐形态

工控机侧建议是：

- ROS2 控制节点
- ROS2 任务编排节点
- ROS2 运动仲裁节点
- ROS2 底盘桥接节点
- HTTP/WS 网关服务
- systemd 托管

### 7.3 推荐模块划分

#### 7.3.1 任务编排节点

职责：

- 持有完整 MissionPlan
- 决定当前执行哪一条垄
- 决定当前处于哪一段转场
- 决定何时停靠、掉头、换垄

#### 7.3.2 直线控制节点

职责：

- 消费融合位姿
- 计算横向误差
- 计算航向误差
- 输出垄内控制速度

#### 7.3.3 运动仲裁节点

职责：

- 区分人工接管、自动作业、急停
- 保证同一时刻只有一个控制源有效

#### 7.3.4 底盘桥接节点

职责：

- 把最终速度转换到底盘控制器协议

#### 7.3.5 网关服务

职责：

- 接收上位机任务
- 读写任务状态
- 暴露统一 HTTP 接口

### 7.4 本地控制保护

工控机控制层必须补以下保护：

- 位姿超时保护
- 横向误差死区
- 航向误差死区
- 角速度限幅
- 角速度变化率限制
- 接近端点时自动降速
- 进入转场时重新切线确认
- 误差过大时停车

---

## 8. 控制逻辑

### 8.1 单垄内部

单垄内部只做：

- 压线保持
- 中间点事件触发
- 到端点减速
- 端点停车

### 8.2 端点掉头

端点掉头建议是状态机，不建议硬切：

1. 接近端点
2. 低速收敛
3. 完全停车
4. 原地旋转
5. 二次切线确认
6. 恢复直线作业

### 8.3 垄间转场

转场不是普通导航，也不是继续追同一条线。

转场段应单独处理：

- 出垄
- 原地转向
- 短距离直行
- 对准下一垄

### 8.4 多垄循环

多垄循环的核心不是“路线更长”，而是：

- 一组垄段
- 一组转场段
- 一个循环状态机

这才是你描述的“来回切换”的正确模型。

## 9. 数据与持久化

### 9.1 当前持久化基础

当前项目已经支持：

- 地图拓扑持久化
- `rowWork` 计划持久化

### 9.2 下一步建议

建议把数据分为两层：

- `rowWork`
  - 单条垄的基础原语
- `rowMission`
  - 多垄穿梭任务编排

### 9.3 文件兼容原则

- 旧地图文件必须可读
- 新文件可以同时保存 `rowWork` 和 `rowMission`
- 普通导航与垄间任务互不破坏

## 12. 风险与对策

### 12.1 风险：把多垄任务写死成单一流程

对策：

- 用任务模板，不用硬编码

### 12.2 风险：把通用导航替代掉

对策：

- 保留普通导航作为兜底

### 12.3 风险：转场段控制过粗

对策：

- 转场段单独建模
- 不和垄内段共用同一套参数

### 12.4 风险：位姿抖动仍然影响控制

对策：

- 工控机本地做降速、死区、跳变过滤
- 后续预留视觉纠偏接口

## 13. 鲁棒性创新增强方案

本节是在前述总体架构基础上的增强设计。

这里不重新推翻前面已经定义的：

- `rowWork` 单垄作业原语
- `rowMission` 多垄任务编排层
- 工控机本地执行闭环

而是在此基础上补三项真正面向稳定性、鲁棒性的增强能力：

- `中心线强跟踪 + 外层容错带`
- `在线误差抑制`
- `任务自愈状态机`

这三项能力不以“重新做路径规划”为重点，而是以：

- 给定任务如何走得更稳
- 位姿波动时如何不抖
- 短时失稳后如何自动恢复

为核心目标。

### 13.1 设计前提

本增强方案基于以下现实约束：

- 工控机当前主要可获得的信息是融合位姿
- 融合位姿的质量判定和基础平滑主要由融合算法自身完成
- 上位机不做高频闭环控制
- 无线链路不适合承载高频控制反馈

因此本方案不再把创新点放在：

- 静态成功率建图
- 固定风险地图
- 远程上位机闭环补偿

而是放在工控机本地执行层。

### 13.2 增强目标

本节三项增强设计要同时解决以下问题：

- 车辆必须仍然“基本严格按预定轨迹行走”
- 不能因轻微位姿抖动而频繁左右摆动
- 不能因短时扰动直接整任务失败
- 不能因一次掉头或一次转场误差就完全失去作业能力

---

### 13.3 中心线强跟踪 + 外层容错带

#### 13.3.1 核心思想

这里不是“用走廊代替中心线”。

正确做法是：

- `中心线` 仍然是主跟踪目标
- `容错带` 只是外层保护层

也就是说：

- 平时始终压着中心线跟踪
- 只有出现短时扰动时，才允许在有限范围内偏离
- 偏离后必须主动回到中心带

#### 13.3.2 为什么这样做

如果只做“细线硬跟踪”，会出现：

- 位姿轻微抖动就触发激烈修正
- 控制量来回震荡
- 实车在垄间反而走得更扭

如果做成“宽走廊随便走”，又会出现：

- 车辆虽然不越界
- 但长期偏在一侧
- 最终不再是真正按预定轨迹作业

所以只能采用分层结构：

- 内层严格跟踪中心线
- 外层提供扰动吸收和恢复边界

#### 13.3.3 分区模型

对每一条 `RowLeg` 或 `Transfer`，定义四层几何约束：

- `centerLine`
  - 预定轨迹中心线
- `centerBandHalfWidth`
  - 中心带半宽
  - 在该范围内认为“基本压线”
- `warningBandHalfWidth`
  - 警戒带半宽
  - 超出中心带后进入保守控制
- `recoveryBandHalfWidth`
  - 恢复边界半宽
  - 超出后禁止继续正常推进，进入恢复

建议垄内直线段的初始参数可采用：

- `centerBandHalfWidth = 0.03 m`
- `warningBandHalfWidth = 0.06 m`
- `recoveryBandHalfWidth = 0.10 m`

建议短转场段的初始参数可采用：

- `centerBandHalfWidth = 0.05 m`
- `warningBandHalfWidth = 0.10 m`
- `recoveryBandHalfWidth = 0.15~0.20 m`

这只是起始值，最终仍需现场整定。

#### 13.3.4 控制语义

每个控制周期，工控机仍然计算：

- 横向误差 `e_lat`
- 航向误差 `e_head`
- 当前路径进度 `s`

然后按区间执行：

1. `|e_lat| <= centerBandHalfWidth`
- 正常模式
- 正常速度
- 正常跟踪增益

2. `centerBandHalfWidth < |e_lat| <= warningBandHalfWidth`
- 保守模式
- 降速
- 增强回中心线趋势
- 禁止过激角速度

3. `warningBandHalfWidth < |e_lat| <= recoveryBandHalfWidth`
- 强保守模式
- 进一步降速
- 优先回中心线
- 任务推进速度明显收紧

4. `|e_lat| > recoveryBandHalfWidth`
- 不再继续正常任务推进
- 进入恢复状态机

#### 13.3.5 必须坚持的原则

为了防止“在保护带内长期偏着走”，必须额外加入以下规则：

- 不在中心带内时，始终存在回中心线的修正驱动力
- 恢复成功的判据不是“回到大走廊内”，而是“回到中心带或中心带附近”
- 长时间偏置在同一侧，也要视为控制质量下降

#### 13.3.6 预期效果

该设计的作用不是让车辆随意偏离，而是：

- 在不放弃压线目标的前提下吸收短时扰动
- 减少高频左右摆动
- 提高垄内运行的平顺性和稳定性

---

### 13.4 在线误差抑制

#### 13.4.1 核心思想

在线误差抑制不是重做定位融合。

它解决的是：

- 融合位姿本身已经可用
- 但其小幅抖动直接进入控制器后，仍会引发过修正

所以这一层要做的是：

- 对“用于控制的误差量”进行在线整形
- 让控制器看到的是“更适合控制”的误差

#### 13.4.2 可直接从位姿导出的量

即使工控机只收到：

- `x`
- `y`
- `yaw`
- `timestamp`

也可以实时导出：

- `e_lat`
  - 横向误差
- `e_head`
  - 航向误差
- `de_lat/dt`
  - 横向误差变化率
- `de_head/dt`
  - 航向误差变化率
- `progressRate`
  - 沿路径推进速度
- `yawRate_est`
  - 基于位姿序列估算的航向变化率

#### 13.4.3 关键处理链路

建议工控机控制层按以下顺序处理误差：

1. 原始位姿投影到参考线
- 计算 `e_lat`、`e_head`、`s`

2. 误差短窗滤波
- 对 `e_lat`、`e_head` 做低通或移动平均
- 避免直接响应瞬时抖动

3. 死区处理
- 当误差足够小时直接视为 0
- 避免车辆在极小误差下频繁修正

4. 变化率抑制
- 当误差在小范围高频震荡时，不立刻放大修正动作

5. 角速度限幅
- 控制器输出角速度设上限

6. 角速度变化率限幅
- 禁止方向指令一周期内突变过大

7. 速度-误差耦合
- 误差越大，允许线速度越低

#### 13.4.4 建议参数

建议在控制层提供以下参数：

- `lateralDeadband`
- `headingDeadbandDeg`
- `lateralFilterWindowMs`
- `headingFilterWindowMs`
- `maxAngularSpeed`
- `maxAngularAccel`
- `conservativeSpeedRatio`
- `recoverySpeedRatio`
- `endpointSlowdownGain`

这些参数建议由工控机侧管理，上位机只负责配置与展示。

#### 13.4.5 模式耦合

在线误差抑制必须与前述“中心线 + 容错带”结合使用：

- 正常区
  - 低增益、柔和控制
- 警戒区
  - 降速、增大回中权重
- 恢复区
  - 暂停正常推进，优先纠偏

#### 13.4.6 预期效果

在线误差抑制的价值在于：

- 让“位姿可用但轻微抖动”的场景也能稳定运行
- 减少方向左右抖动
- 降低地面颠簸对控制的放大效应
- 在不修改融合算法的前提下提升实车稳定性

### 13.5 任务自愈状态机

#### 13.5.1 核心思想

传统流程往往是：

- 正常就执行
- 异常就停机

这对现场作业不够鲁棒。

本方案要求：

- 轻微异常先降级
- 中等异常尝试恢复
- 恢复失败后再故障退出

也就是说：

- 任务不是线性流水线
- 而是带有恢复分支的状态机

#### 13.5.2 自愈状态机作用范围

该状态机主要作用于：

- `RowLeg`
- `Transfer`
- `Turn`

其中：

- `RowLeg` 重点处理垄内偏移和重新压线
- `Transfer` 重点处理短转场过程中的重新进入轨迹
- `Turn` 重点处理端点原地转向失败后的精调与重试

#### 13.5.3 建议状态

建议执行层至少定义以下状态：

- `Tracking`
  - 正常跟踪
- `Conservative`
  - 保守跟踪
- `RecoveryAlign`
  - 停止正常推进，优先回正
- `RecoveryAdvance`
  - 低速重新进入中心带
- `Paused`
  - 人工暂停
- `ManualOverride`
  - 人工接管
- `Fault`
  - 恢复失败或严重异常

#### 13.5.4 典型触发条件

在只依赖融合位姿的前提下，仍可用以下触发条件：

- `|e_lat|` 持续超出警戒带或恢复带
- `|e_head|` 持续过大
- 一段时间内 `progress` 几乎不增长
- 角速度指令长期接近饱和但误差不下降
- 端点附近反复无法稳定进入掉头状态
- 转场后无法重新回到中心带

#### 13.5.5 恢复动作

建议分三级恢复：

1. 轻微异常
- 切保守模式
- 降速
- 继续尝试回中心

2. 中等异常
- 暂停正常推进
- 先回正航向
- 再低速靠回中心带

3. 严重异常
- 停车
- 执行有限次数重试
- 超过上限后进入 `Fault`

#### 13.5.6 与 `rowMission` 的关系

建议在 `rowMission` 层面预留以下任务策略：

- 每步最大恢复次数
- 每步最大无进展时间
- 恢复失败后的策略
  - 重试当前步
  - 回退到安全步
  - 整任务故障退出

这意味着：

- 自愈状态机不是单独的控制补丁
- 而是任务模型的一部分

#### 13.5.7 预期效果

任务自愈状态机的主要收益是：

- 轻微扰动不再直接导致整任务失败
- 掉头、进垄、转场的容错性显著提升
- 系统现场连续作业能力更强

---

### 13.6 三项增强之间的关系

这三项增强不是平行孤立的，而是分层协同：

1. `中心线强跟踪 + 外层容错带`
- 定义“允许偏多少”

2. `在线误差抑制`
- 定义“偏了以后如何平稳纠正”

3. `任务自愈状态机`
- 定义“纠不回来时如何恢复”

从工程角度看，三者构成：

- 几何约束层
- 控制整形层
- 执行恢复层

### 13.7 与当前已完成部分的关系评估

本节非常重要。

当前增强方案并不是推翻之前已经完成的设计，而是：

- 以现有 `rowWork` / `rowMission` 为基础
- 在其上继续扩展控制语义与状态语义

#### 13.7.1 可以直接继承、不需要推翻的部分

以下内容可以继续保留：

- `rowMission` 多垄任务编排模型
- 上位机右侧任务编辑 UI 的基本结构
- 地图文件中 `rowWork` / `rowMission` 的持久化框架
- 工控机本地执行闭环这一总体原则

这些内容属于“基础架构已经正确”，不需要重做。

#### 13.7.2 属于增量扩展的部分

以下内容主要属于增量开发：

- 在 `RowLeg` / `Transfer` 上增加中心带、警戒带、恢复带参数
- 在工控机状态接口中增加：
  - 当前控制模式
  - 当前恢复状态
  - 当前横向误差与航向误差
  - 最近恢复事件
- 在上位机状态页中展示：
  - 正常 / 保守 / 恢复 / 故障
  - 当前步骤恢复次数
  - 当前是否已回到中心带
- 在地图界面上增加中心线与容错带的可视化

这些扩展建立在现有结构之上，不需要推翻当前已完成的主干。

#### 13.7.3 需要修改之前已完成设计定义的部分

以下内容不属于简单新增，而是对之前方案的明确修正：

1. 不能再把“走廊”描述成对中心线的替代
- 正确表述应改为：
  - `中心线强跟踪 + 外层容错带`

2. `RowLeg` 和 `Transfer` 的控制语义需要升级
- 之前更偏向“沿直线执行”
- 现在要升级为：
  - 带中心带、警戒带、恢复边界的分层执行原语

3. 任务执行层不能再只定义“开始/暂停/停止”
- 需要引入更细的执行状态：
  - `Tracking`
  - `Conservative`
  - `RecoveryAlign`
  - `RecoveryAdvance`
  - `Fault`

也就是说：

- 之前完成的是“基础任务编排框架”
- 现在补的是“鲁棒执行语义”

#### 13.7.4 对上位机侧的影响评估

上位机侧总体结论是：

- `不是推翻重做`
- `是结构保留、数据扩展、状态展示增强`

需要新增或修改的重点是：

- `rowWork` / `rowMission` 参数编辑区
- 地图可视化表达
- 状态展示区
- 后续 `rowMission` 通信接口

但当前已经完成的：

- 任务编辑骨架
- 持久化骨架
- 单垄与多垄分层结构

都是可以继续使用的。

#### 13.7.5 对工控机侧的影响评估

工控机侧总体结论是：

- `需要明显升级`
- `但不是完全重写`

原因是：

- 之前工控机执行层主要是“能执行作业”
- 现在要求升级为“执行时能自稳、能降级、能恢复”

因此工控机侧需要补：

- 分层误差区间控制
- 在线误差整形
- 恢复状态机
- 更细的状态输出接口

这部分属于真正的主开发量。

---

### 13.8 推荐实施顺序

建议按以下顺序实施：

1. 先补 `中心线强跟踪 + 外层容错带`
- 最容易形成可视化和参数化结果

2. 再补 `在线误差抑制`
- 对稳定性提升最大

3. 最后补 `任务自愈状态机`
- 对鲁棒性和现场可用性提升最大

这样做的原因是：

- 先定义清楚几何约束边界
- 再把正常控制做稳
- 最后再补异常恢复

---

### 13.9 本节结论

在当前“工控机侧主要拿融合位姿、上位机不做高频闭环”的前提下，
真正值得做的不是重新发明一套复杂路径规划算法，而是：

- 用 `中心线强跟踪 + 外层容错带` 保证“基本严格按轨迹走”
- 用 `在线误差抑制` 保证“位姿抖动下仍然平稳”
- 用 `任务自愈状态机` 保证“短时异常后仍能恢复”

这三项设计与前面已经完成的 `rowWork + rowMission` 基础框架是兼容的，
整体上属于：

- `基础架构不推翻`
- `执行语义显著增强`

---

## 14. 结论

你的真实需求，不是“在地图上走一条蛇形线”，而是：

- 以垄为单位执行
- 以转场为边界切换
- 以状态机控制节拍
- 以本地控制保证稳定性

所以正确路线是：

- 保留当前上位机的通用地图与任务能力
- 把 `rowWork` 作为单垄作业原语
- 在其上新增 `rowMission` 多垄任务编排层
- 把高频控制放到工控机本地执行

这就是本项目后续应该继续完善的框架和基础。
