## 1. 结论

**目前不能认定“除实车部署和测试外，整个系统已经完成完整功能验证”。** 更准确的状态是：架构主链路已经实现，已有自动化测试通过，正常任务和若干异常场景已经得到仿真验证；生产融合输入、任务恢复、持久化边界和长期运行仍有缺口。本轮还复现了现有测试没有发现的缺陷。

“上位机规划和下发任务、工控机闭环执行、手动 WebSocket 直通底盘”的分工适合当前需求，没有发现需要推翻架构的理由。当前应优先补齐正确性和恢复能力，再做有证据的精简；现有轻量回环测量没有显示 Pure Pursuit 计算本身是瓶颈。

本次是审查，未修改两仓库的生产源码、配置或 Git 分支；新增报告和临时复现材料。没有连接或控制真实车辆。继续遵守手动、自动两条通道独立的约定，不引入控制权仲裁。`script/` 的 53 个文件与既有基线逐一核对，路径及 SHA256 均未变化。

## 3. 优先修复的问题

P1：建议在下一轮完整软件验收前修复。P2：明确的行为缺陷或稳定性缺口。P3：显示、维护与清理问题。以下说明区分实际复现和静态发现。

### F01 · P1 · 一条错误请求可把任务服务锁定成存储故障

**已用实际 C++ 回环服务复现。** 获取有效会话后，上传 `context=[]` 的任务，返回 `503 operation_failed`；`health.storageHealthy` 变成 false，随后正确任务持续返回 `503 storage_unhealthy`。提交纬度为 91 的原点同样触发。

根因是 [tracking_service.cpp:513](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/tracking_node/src/tracking_service.cpp#L513) 把非预期 `std::exception` 无差别视为存储故障并锁存；嵌套 JSON 类型异常和原点校验异常也进入此分支。执行中的任务还可能因此进入存储故障暂停。

建议：入口严格校验字段类型；把输入错误映射为 4xx；仅实际 I/O/存储错误改变存储健康。补回归验证“错误请求被拒绝后，下一条正常请求仍成功”。

### F02 · P1 · 请求历史写得进去，却无法在重启时读取

**已用实际服务复现，包括完全符合现有任务结构的输入。** 六份标准任务，每份四步、总计 76,000 个点，请求约 3.29 MB，均得到 `202` 且准备成功。`metadata/requests.json` 累计 **19,094,363 字节** 后正常停止服务，重启退出码为 1，报 `document_unavailable`。

该轮标准大任务探针把临时会话期限设为 10 秒，以隔离存储边界；默认期限下，使用被接口接受的附加字段构造大请求也复现同样问题。

根因：去重账本保存完整请求正文，[protocol.cpp:153](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/tracking_node/src/protocol.cpp#L153)；每次接受请求又全量落盘，[tracking_service.cpp:131](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/tracking_node/src/tracking_service.cpp#L131)。[storage.cpp:68](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/control_common/src/storage.cpp#L68) 读取单文件限制为 16 MiB，写入仅受整个存储目录 128 MiB 预算约束。

建议：统一读写限制，去重记录保存规范化内容摘要和必要结果，按记录或分段存储并在线淘汰。摘要应采用可靠哈希并保留“同 ID 不同内容拒绝”的语义。不能只把读取上限扩大，否则全量重写、恢复耗时和增长问题仍存在。

### F03 · P1 · 编码器错误 JSON 可使整个融合进程退出

**当前解析函数离线提取后已复现。** `{"msg":{"console":{}}}`、`{"msg":3}`、`[]` 均抛出 JsonCpp 异常。[encoder_handler.cpp:282](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/sensor_fusion/src/encoder_handler.cpp#L282) 没有完整检查对象和字符串类型；[接收线程:183](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/sensor_fusion/src/encoder_handler.cpp#L183) 没有相应异常边界，异常逃出线程入口将调用 `std::terminate`。

探针使用当前源码原函数，ROS 时间与日志为最小替身，证明解析器抛异常；线程退出后果由现有调用链和 C++ 线程规则确认，没有声称运行了完整 ROS 进程崩溃测试。

建议：类型校验、逐报文异常隔离和错误计数；坏报文不能终止融合，也不能更新有效编码器观测时间。

### F04 · P1 · 上位机重开或重新应用配置后无法接续原暂停任务

**Qt 临时白盒夹具与回环 HTTP 已复现。** 暂停任务后重开客户端，即便加载同一地图、获得新操作会话并成功回读相同 taskId/revision/context，继续操作仍被拒绝。

[trackingclient.cpp:34](https://github.com/DAC-Code25/Tenco/blob/master/trackingclient.cpp#L34) 在 stop 时清空 `preparedPlan`；[回读:346](https://github.com/DAC-Code25/Tenco/blob/master/trackingclient.cpp#L346) 只发出信号，地图只显示元数据。[controlsessioncoordinator.cpp:59](https://github.com/DAC-Code25/Tenco/blob/master/controlsessioncoordinator.cpp#L59) 又要求该本地计划匹配远端任务。配置保存会重新配置客户端，也能触发此路径。

“重新上传”不能保留执行进度，因为 [task_executor.cpp:87](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/tracking_node/src/task_executor.cpp#L87) 在 Paused 时拒绝 prepare；现有绕过方式是中止并新建 execution。

建议：增加“回读并确认接续”流程，验证远端任务正文/摘要/版本/坐标上下文后恢复本地任务身份，再允许显式继续。工控机保持独立执行，不需要上位机在线保活。

### F05 · P1 验证项 · UKF 对外的控制可靠性可能没有反映 RTK 质量退化

**代码链路明确，完整 ROS 场景尚未复现，不能当作已经实测确认的错误运动。** 生产默认 UKF；`soft_quality_gate=true` 允许非 FIX 或低卫星数数据降权进入滤波，[fusion_node.cpp:4175](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/sensor_fusion/src/fusion_node.cpp#L4175)。但 [ukf_fusion.cpp:2641](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/sensor_fusion/src/ukf_fusion.cpp#L2641) 设置控制可靠性时仅看观测时间、残差门禁和双天线基线，没有使用已计算的 position/heading quality 或 FIX/卫星状态。

预期需要验证的条件：系统已暖机、标定及定位策略已验证；双 RTK 丢 FIX，但坐标连续、基线正常且残差仍通过。这可能持续刷新“可靠”观测，[pose_builder.cpp:83](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/control_common/src/pose_builder.cpp#L83) 仍使用固定保守误差界，使 `validForControl/nominal` 未随质量退化改变。

建议：明确低质量观测允许参与估计与允许控制使用的不同判据；增加 FIX→退化→恢复的真实 UKF/ROS 回归，检查质量、时间戳、误差界与控制可用性是否一致。不是要求把软降权滤波直接删除。

### F06 · P2 · RTK 无效数值仍被标成有效

**原解析函数离线已复现。** 校验和正确但纬度是 `garbage`、`nan`、`91.0`、`30.1garbage` 的报文，分别得到 0、NaN、91、30.1，且 `valid=true`。

[rtk_parser.cpp:317](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/sensor_fusion/src/rtk_parser.cpp#L317) 转换失败后仅记录日志，[有效性:371](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/sensor_fusion/src/rtk_parser.cpp#L371) 最终只看原字符串非空。建议完整消费字符串，验证 finite、经纬度范围、定位模式和卫星数，并覆盖启动阶段坏数据。尚未实测这些输入对完整滤波输出的具体影响。

### F07 · P2 · 编码器缺少右轮值时会把一个数字拆成两个

**离线已复现。** `wheelencode : 12345` 被解析成左轮 1234、右轮 5。[encoder_handler.cpp:295](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/sensor_fusion/src/encoder_handler.cpp#L295) 两个数之间使用 `\s*`，正则回溯允许零分隔拆分。

建议：匹配两个完整数值和明确分隔，检查范围、尾部格式；可同时把每条消息重编译正则改为固定解析器。保持现有 Lua 文本格式，不需要修改 Lua。

### F08 · P2 · 急停请求重放绕过幂等语义

**回环服务已复现。** 同一急停请求首次成功后，将故障复位到 Idle；重放完全相同 requestId/正文，接口返回旧 commandId 和 HTTP 200，但执行器再次进入 `Fault/emergency_stop`。

[tracking_service.cpp:194](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/tracking_node/src/tracking_service.cpp#L194) 在正常去重之前设置 `emergency_`；稍后的去重不能撤销副作用。建议保留停止快通道，并使已处理的旧请求不再次影响新状态。不要为修复幂等把停止排到慢存储队列之后。

### F09 · P2 · 已完成执行的历史终态会被后续停止覆盖

**回环服务已复现。** 定时任务已经 `Completed/succeeded` 后按自动停止，同一 execution 文件被改为 `Fault/emergency_stop`。

[task_executor.cpp:247](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/tracking_node/src/task_executor.cpp#L247) 直接复用 fail，仍保留旧 executionId，[tracking_service.cpp:740](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/tracking_node/src/tracking_service.cpp#L740) 覆写旧历史。建议已结束 execution 的结果保持不变，区分当前控制器停止状态与过去任务结果。

### F10 · P2 · 执行中的事件未持久化，进程丢失后无法完整补读

**回环服务已复现。** external_ack 等待时，实时接口已有开始、检查点到达、拍照请求三个事件；执行文件只有 `lastEventSeq`，没有事件正文。结束进程再启动后，历史改为 Aborted，但这些事件丢失。

[tracking_service.cpp:734](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/tracking_node/src/tracking_service.cpp#L734) 仅在终态把内存事件写入执行文件。与总体方案中“有序事件、拍照 intent 和结果持久化”的要求存在差距。

建议：执行中增量持久化事件及确认结果，明确事件 ID、顺序和保留边界。不能把状态版本/最后序号当作完整事件历史。此问题不意味着当前程序已发生重复拍照；未知结果仍应维持人工核对语义。

### F11 · P2 · 旋转地图视图会误使任务计划失效

**Qt 夹具已复现。** Paused 时将视图旋转 30°再继续，mapRevision 从 1 增加到 2，preparedPlan 清空。[map.cpp:3504](https://github.com/DAC-Code25/Tenco/blob/master/map.cpp#L3504) 把显示旋转纳入地图比较数据，[map.cpp:3568](https://github.com/DAC-Code25/Tenco/blob/master/map.cpp#L3568) 又用于任务指纹；该旋转实际只改变视图，不改变路径坐标。

建议将“文件是否需要保存”和“任务几何/参数是否改变”的比较数据分开；保留任务指纹校验，排除纯展示字段。

### F12 · P2/P3 · 操作反馈和定位显示语义不一致

**Qt 夹具已复现两项。**

- 多垄任务上传失败或成功时，[map.cpp:5186](https://github.com/DAC-Code25/Tenco/blob/master/map.cpp#L5186) 写的是单垄页状态；多垄页仍可显示“待命”。建议让当前任务页或统一反馈区显示操作结果。
- 定位不可用后，随后到达坐标版本匹配但 `validForControl=false` 的位姿，[map.cpp:5131](https://github.com/DAC-Code25/Tenco/blob/master/map.cpp#L5131) 会重新设置“有车辆位置”。这是显示语义问题，没有证明能绕过自动任务门禁。建议区分最后已知位置与当前有效位置，失效时显示年龄/变灰。

## 4. 稳定性和性能审查

### 4.1 本轮实际测量

Windows 本机 MinGW Debug 服务、回环 WebSocket 底盘模型、注入模拟位姿、执行长直线路径；两个阶段各约 15 秒。每个阶段末读取服务最近 256 次控制循环统计，约覆盖 12.8 秒。四路读取为 status/health 请求，另有模拟位姿输入和会话心跳。

| 指标 | 单路状态读取 | 四路并发读取 |
|---|---:|---:|
| 成功读取数 | 138 | 1,920 |
| 读取吞吐 | 9.15 次/秒 | 127.80 次/秒 |
| API 平均耗时 | 1.925 ms | 2.756 ms |
| API P99 | 5.658 ms | 5.739 ms |
| 控制计算 P99 | 0.104 ms | 0.111 ms |
| 控制实际间隔 P99 | 63.617 ms | 63.532 ms |
| 控制周期超过 100 ms 次数 | 0 | 0 |
| 请求错误/worker 拒绝 | 0/0 | 0/0 |

全程维持 Tracking，存储健康。P99 表示约 99% 的样本不超过该值。控制目标周期为 50 ms；Windows 调度抖动在间隔统计中可见。

这些结果仅说明该短时回环条件下，控制计算及普通读取尚有余量。**不包含 UKF 全部计算、真实 ROS 调度、视频/录像负载、实际网络或目标工控机性能，也不是小时级稳定性结论。** 原始结果和探针在本报告末尾链接。

### 4.2 比微调 Pure Pursuit 更值得处理的工作

1. **历史在线清理。** [tracking_service.cpp:41](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/tracking_node/src/tracking_service.cpp#L41) 的 tasks/executions/commands 七天清理仅在启动运行，内存 commandResults 也持续增长。常驻进程需要分批在线淘汰，保留活动任务及必须的幂等窗口。尚未运行到 128 MiB 极限，不能报告具体可运行天数。
2. **停止无意义的终态落盘。** [tracking_service.cpp:656](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/tracking_node/src/tracking_service.cpp#L656) 每 20 tick 调用 persist，保留 executionId 时即使任务完成且无状态变化，也每秒全量写执行记录、序列化事件并 fsync。应变化时写快照、终态写一次；当前写入还刷新文件 mtime，影响按时间清理。
3. **减少全目录扫描和全量账本写入。** [storage.cpp:183](https://github.com/DAC-Code25/sensor-fusion-ros2/blob/main/control_common/src/storage.cpp#L183) 每次 put 遍历整个存储目录；JSON 也重复序列化。维护存储用量与增量日志能同时减少 I/O 和恢复复杂度。
4. **保障任务操作响应。** 大任务解析/准备/持久化与心跳、查询共用一个 worker。默认 1 秒会话期限下，大任务探针曾触发会话过期；没有用隔离基准量化最坏时延。应补最大合法任务压力测试，按测量结果把慢准备工作与轻量请求处理分开，并保持状态提交顺序；不应简单放宽全部超时掩盖阻塞。
5. **限制 UI 日志。** [home.cpp:905](https://github.com/DAC-Code25/Tenco/blob/master/home.cpp#L905) 持续追加日志，未发现显示控件的最大 block 数设置。交替错误会持续增长，应限定显示行数；磁盘日志继续按既有轮转策略保留。
6. **减少纯视图操作重建。** 旋转滑块会刷新网格、点、路径后再旋转视图。纯旋转可仅改变视图变换；收益应以大地图测量确认。

HTTP 当前每个响应关闭连接，会增加高频轮询的连接成本，但上述短测未显示它是首要瓶颈。先处理持久化和 worker 阻塞；后续有测量依据再评估 keep-alive 或调整轮询，暂不需要为此增加新通信体系。

### 5.2 应保留的复杂性

- **Pose HTTP 与 ROS 两种出口：**服务于上位机显示/示教与工控机本地闭环，有不同用途。
- **requestId、stateVersion、任务版本及坐标/标定版本校验：**防止重复执行、旧指令影响新状态、旧坐标任务误运行。应修复实现缺口，不能整套删除。
- **短时 motionPermit 和任务操作会话：**用于任务 API 的显式启动及陈旧请求拒绝，不是手动通道许可，也不应成为自动行驶保活依赖。可根据压力测试调整实现，不能把它误认为底盘控制权协议。
- **暂停/减速停稳/转向/等待等状态：**对应真实执行阶段；应收敛重复状态来源，而非简单减少状态数。
- **观测年龄、实测轮速、新旧连接代次、发送截止和有界队列：**分别处理传感器过期、实际停稳、重连重放、积压与时效，有明确作用。
