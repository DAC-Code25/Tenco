# 开发流程与规范

本文件是供开发者快速阅读的流程说明。仓库根目录 `AGENT.MD` 是开发代理必须遵守的完整强制规范；两者不一致时，以用户当前明确要求和 `AGENT.MD` 为准。

## 1. 一项任务一条完整链路

每项新增功能、功能改进、重构或缺陷修复必须遵循：

```text
保存 IDE 内容
  -> 检查并交付旧修改
  -> 同步远程默认分支
  -> 创建独立任务分支
  -> 先写中文开发方案
  -> 实施最小化修改
  -> 新建并更新中文开发记录
  -> 固定 Qt Kit 配置、构建、测试
  -> 对照方案复核
  -> 中文 Commit
  -> 推送新分支
  -> 中文 PR 或完整中文 PR 描述
```

不得把多项无关需求混入同一分支、同一方案或同一开发记录。

## 2. 修改前基线检查

开始前先保存 Qt Creator 中的全部文件，然后执行：

```powershell
git status --short --branch
git diff --check
git diff
git diff --cached
git branch --show-current
git remote -v
git log -5 --oneline --decorate
```

如果存在旧修改或未推送提交：

1. 先确认归属和完整性，不覆盖、不还原、不隐藏用户工作。
2. 属于上一项已完成任务时，补齐记录并完成构建测试。
3. 使用中文说明提交并推送当前分支。
4. 创建 PR；没有可用的 GitHub 工具时，至少准备完整中文 PR 标题和描述。
5. 归属不清或内容未完成时，停止切换分支并请用户确认。

工作区和上一任务妥善交付后，才允许同步基线。仓库当前使用远程 `Tenco` 和默认分支 `master`，执行时仍需复核：

```powershell
git fetch Tenco --prune
git switch master
git pull --ff-only Tenco master
```

只允许快进同步；出现分叉时不得擅自 merge、rebase 或强推。

## 3. 分支策略

从最新默认分支为每项任务创建独立分支：

- `feature/<topic>-v<n>`：新增功能。
- `fix/<bug>-v<n>`：缺陷修复。
- `refactor/<area>-v<n>`：行为不变的重构。
- `perf/<area>-v<n>`：性能优化。
- `docs/<topic>-v<n>`：文档与流程。
- `build/<topic>-v<n>`：构建、依赖和 CI。

`master` 必须保持可构建、测试可通过，不直接在其上开发，不强推。

## 4. 方案先于代码

修改代码前，必须在 `docs/develop/` 新建以中文为主体的开发方案文件。方案至少说明：

- 日期、分支、背景、现状、目标和非目标。
- 设计、候选方案、取舍和最小改动边界。
- 预计修改的模块、文件、接口、配置和数据。
- 性能、稳定性、可靠性、安全性、兼容性和无关模块影响。
- 风险、回滚、构建、测试和验收方式。

方案文件不能覆盖历史方案。需求或实施范围实质变化时，先更新方案及原因再继续修改。

## 5. 开发记录

每项任务必须另建一份新的中文开发记录，至少包含：

- 任务、类型、日期、基线、开发分支和对应方案。
- 修改前 Git 状态与远程同步结果。
- 新增、修改、删除内容及原因。
- 实际影响、关键取舍、风险和已知限制。
- 配置、构建、测试命令和真实结果。
- Commit、推送分支、日期、结果和 PR 信息。

记录随执行过程更新，不能在动作发生前预填“已通过”或“已推送”。

## 6. 实施原则

- 先定位根因和调用链，再修改。
- 只改与方案直接相关的内容，不夹带无关重构和批量格式化。
- 保持公开 API、配置、地图/任务文件和网络协议兼容。
- UI 更新必须在 UI 线程；worker 生命周期、停止顺序和资源释放必须明确。
- 网络和设备操作必须有超时、取消、重连退避和离线处理，不能阻塞 UI。
- 运动控制必须保证急停优先、命令互斥和失联停止。
- 环境参数进入 `config.json`/`ConfigManager`，敏感信息不得写入日志或仓库。
- 新逻辑优先进入可测试的小模块，避免继续扩大大型 UI 协调类。

## 7. 固定构建与测试

本机验收固定使用：

- Qt 6.5.3 MinGW 64-bit。
- MinGW 11.2 64-bit。
- Ninja。
- Debug。
- 构建目录 `build/Desktop_Qt_6_5_3_MinGW_64_bit-Debug`。
- `BUILD_TESTING=ON`、`TENCO_BUILD_TESTS=ON`。
- QML debugging and profiling Enable。

完整路径和标准命令见 `docs/02_Build_and_Run.md` 与根目录 `AGENT.MD`。

每次完成后必须执行：

1. CMake 配置。
2. Tenco 与全部测试目标的完整构建。
3. `ctest --output-on-failure`。
4. 与改动相关的单元、集成、GUI 或设备测试。
5. `git diff --check` 和方案符合性复核。

失败时继续定位、修复并重新验证。外部设备或服务不可用时，记录未执行项、原因、风险和人工步骤，不得伪报通过。

## 8. 中文提交规范

每次提交聚焦一个主题，冒号后的标题和正文全部使用中文：

- `feat: 新增……`
- `fix: 修复……`
- `refactor: 重构……`
- `perf: 优化……`
- `test: 补充……测试`
- `docs: 更新……文档`
- `build: 调整……构建配置`
- `chore: 完成……维护`

提交前审查暂存差异，排除机密、构建产物和无关修改。

## 9. PR 与自我评审

PR 标题和描述必须使用中文，并至少包含：

- 背景和问题。
- 本次修改。
- 设计与取舍。
- 影响范围、风险和兼容性。
- 实际构建与测试结果。
- 尚需人工完成的 GUI/设备验证。
- 对应方案与开发记录。

无法直接创建 PR 时，应提供 GitHub Compare 链接和可直接复制的完整中文 PR 内容。

## 10. 完成定义

只有基线干净、独立分支、方案、实现、开发记录、固定 Kit 完整构建、CTest、专项验证、方案复核、中文提交、推送以及 PR 交付全部完成后，任务才可报告完成。详细检查表见根目录 `AGENT.MD`。
